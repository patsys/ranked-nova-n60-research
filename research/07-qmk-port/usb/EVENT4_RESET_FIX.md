# Raw USB event 4 endpoint reset correction

The C engine previously acknowledged raw controller event 4 without executing the original class callback. Native dispatch at 0xed66 calls table+4 (0x4858). The corrected engine preserves its hardware writes: acknowledge 0x40017eac=16, IN mask 0x40017eb0=7, enable IN1 and IN2 through separately masked RMWs at 0x40017f78, OUT mask 0x40017eb4=9, enable OUT3 through masked RMW at 0x40017f7c, and rearm OUT3 at 0x40017f2c=127. It does not reset the PHY or invoke controller initialization again.

Native software evidence: 0x4858 clears context+10/+11, copies configuration descriptor bmAttributes to context+9, marks all six readiness words at 0x20001340 ready, sets bus state byte 0x2000051c to 1, and clears 0x20000528. Dispatch additionally sets 0x2000051d=1 and clears 0x20000424, 0x20000508 and 0x2000050c. These are measured instruction effects. The C engine clears its configuration, pending address, transfer reply/length/state and wakeup caches and notifies configured(0), representing reset in its own structures; those C fields are not claimed to be exact native RAM layouts. No hardware address register behavior is invented.

`validate_usb_device.py` executes the actual native event dispatcher and callback without bypassing functions, compares the C MMIO trace, checks native software memory and C stale-transfer cleanup, and retains previous ack-only behavior as a negative control. Seeded high bits verify the native six-bit mask. It also runs the actual outer 0x312c IRQ wrapper and compares its status acknowledgement with C. Physical acknowledgement side effects and electrical enumeration cannot be proved by ordinary-memory MMIO emulation.

Other events: event 2 at 0xed46 calls 0xe000, a direct return. Event 3 at 0xed50 calls 0x30e0 (RAM marker clear), then conditionally 0xd4b4 (application RAM flags and, for application state 5, 0x3f00). No additional direct USB controller writes appear there. Event 1 executes application frame/scheduler work; the port has its own frame callback. These application policies are not silently transplanted into the USB transport. The raw event 4 physical event name remains unverified without controller documentation.

This fixes a definite omission, but does not establish the cause of either physical QMK enumeration failure. No hardware operation, firmware target rebuild, manifest update, or flash was performed by this correction. Future physical diagnostics should use a bounded RAM test and retain the working stock recovery path. Do not reset the USB controller while relying on the current boot USB channel to return a register snapshot.
